# تراکنش و همزمانی در EF

---

## `SaveChanges` خودش یک تراکنش است

این نکته‌ای است که خیلی‌ها نمی‌دانند:

```csharp
p1.Stock -= 1;
p2.Stock -= 1;
db.SaveChanges();      // هر دو UPDATE در یک تراکنش
```

اگر دومی شکست بخورد، اولی هم rollback می‌شود. **اتمیک بودن خودکار است.**

## پس کِی تراکنش صریح لازم است؟

وقتی **چند `SaveChanges`** داری و می‌خواهی همه با هم اتمیک باشند:

```csharp
using (var transaction = db.Database.BeginTransaction())
{
    try
    {
        db.SaveChanges();    // اول
        db.SaveChanges();    // دوم
        transaction.Commit();
    }
    catch
    {
        transaction.Rollback();
        throw;
    }
}
```

یا وقتی می‌خواهی EF و ADO.NET خام را در یک تراکنش ترکیب کنی.

## مشکل همزمانی: Lost Update

این سوال را زیاد می‌پرسند چون مشکل واقعی و رایجی است.

**سناریو:**

| زمان | کاربر A | کاربر B | Stock در دیتابیس |
|---|---|---|---|
| ۱ | می‌خواند → 10 | | 10 |
| ۲ | | می‌خواند → 10 | 10 |
| ۳ | ۳ تا کم می‌کند → 7 | | **7** |
| ۴ | | ۲ تا کم می‌کند → 8 | **8** |

جمعاً ۵ تا فروخته شد، ولی موجودی ۸ است. **تغییر کاربر A گم شد.**

## راه‌حل ۱: Optimistic Concurrency

«خوش‌بینانه» یعنی فرض می‌کنیم تعارض به‌ندرت پیش می‌آید، پس قفل نمی‌زنیم — فقط **موقع نوشتن چک می‌کنیم** که کسی وسط کار چیزی عوض نکرده باشد.

```csharp
[Timestamp]
public byte[] RowVersion { get; set; }
```

`RowVersion` ستونی است که SQL Server با **هر تغییر** خودکار مقدارش را عوض می‌کند.

EF موقع `SaveChanges` این SQL را می‌زند:

```sql
UPDATE Products
SET Stock = @newStock
WHERE Id = @id AND RowVersion = @originalVersion
```

اگر کسی دیگر رکورد را عوض کرده باشد، `RowVersion` جور در نمی‌آید، هیچ سطری آپدیت نمی‌شود، و EF یک `DbUpdateConcurrencyException` پرتاب می‌کند.

### سه استراتژی برای حل تعارض

| استراتژی | کِی مناسب است |
|---|---|
| **برنده کاربر** (Client Wins) | مقدار ما را زورکی بنویس |
| **برنده دیتابیس** (Store Wins) | تغییر ما را دور بریز |
| **از کاربر بپرس** | داده هر دو را نشان بده و بگذار او تصمیم بگیرد |

در سیستم‌های مالی معمولاً گزینه سوم درست است.

## راه‌حل ۲: عملیات اتمیک در دیتابیس

برای شمارنده‌ها (مثل موجودی انبار) اغلب این راه بهتر است:

```sql
UPDATE Products
SET Stock = Stock - @qty
WHERE Id = @id AND Stock >= @qty
```

**چرا بهتر است؟** چون هیچ فاصله‌ای بین خواندن و نوشتن وجود ندارد. دیتابیس خودش خواندن و کم کردن را اتمیک انجام می‌دهد.

شرط `Stock >= @qty` هم جلوی منفی شدن موجودی را می‌گیرد. اگر تعداد سطرهای تحت تأثیر صفر باشد، یعنی موجودی کافی نبوده.

---

## Optimistic در برابر Pessimistic

| | Optimistic | Pessimistic |
|---|---|---|
| روش | چک کردن موقع نوشتن | قفل کردن موقع خواندن |
| مناسب برای | تعارض کم | تعارض زیاد |
| ریسک | ممکن است کار کاربر هدر برود | deadlock و کندی |
| در EF | `[Timestamp]` | `UPDLOCK` در SQL خام |

**در وب تقریباً همیشه Optimistic درست است**، چون نمی‌توانی رکوردی را قفل کنی و منتظر بمانی کاربر فرم را پر کند — ممکن است اصلاً برنگردد.

## چرا EF در درج انبوه کند است؟

```csharp
foreach (var p in products)
    db.Products.Add(p);      // با ۱۰ هزار رکورد خیلی کند
```

**دلیل:** EF بعد از هر `Add` متد `DetectChanges` را صدا می‌زند که **تمام** موجودیت‌های ردیابی‌شده را بررسی می‌کند. یعنی پیچیدگی O(n²).

**بهبود اول:**
```csharp
db.Configuration.AutoDetectChangesEnabled = false;
// ... افزودن رکوردها ...
db.Configuration.AutoDetectChangesEnabled = true;
db.SaveChanges();
```

**ولی همچنان:** `SaveChanges` به‌ازای هر رکورد یک `INSERT` جداگانه می‌زند.

**برای حجم واقعاً بالا** باید سراغ این‌ها بروی:
- `SqlBulkCopy` (بومی ADO.NET، سریع‌ترین)
- کتابخانه `EFCore.BulkExtensions` یا `EntityFramework.Extended`
- Stored Procedure با Table-Valued Parameter

**جمله‌ای که سر مصاحبه خوب است:**
> «EF برای کار با تعداد کم موجودیت عالی است. برای درج یا آپدیت انبوه، من از SqlBulkCopy یا Stored Procedure استفاده می‌کنم — چون EF ذاتاً برای این کار ساخته نشده.»

## طول عمر DbContext

**قانون: کوتاه.** در ASP.NET، یک نمونه برای هر درخواست HTTP.

**چرا نه طولانی؟**
- Change Tracker مدام بزرگ‌تر می‌شود → مصرف حافظه بالا می‌رود
- `DetectChanges` کندتر و کندتر می‌شود
- کش سطح اول داده کهنه نگه می‌دارد
- `DbContext` **thread-safe نیست** — استفاده همزمان از چند رشته خطا می‌دهد

**چطور پیاده می‌شود؟** با IoC Container، `DbContext` را با طول عمر per-request ثبت می‌کنی. در Unity و Autofac این گزینه استاندارد است.
