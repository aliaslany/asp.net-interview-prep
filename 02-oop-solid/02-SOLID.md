# اصول SOLID

پنج اصل طراحی که هدف همه‌شان یک چیز است: **کدی که تغییر دادنش نترساند.**

---

## S — Single Responsibility

> هر کلاس باید فقط **یک دلیل برای تغییر** داشته باشد.

**تعریف دقیق‌تر:** هر کلاس باید فقط به یک گروه ذی‌نفع پاسخگو باشد.

### مثال نقض

```csharp
public class BadOrderService
{
    public void ProcessOrder(Order order)
    {
        // اعتبارسنجی      ← تیم کسب‌وکار
        // ذخیره در دیتابیس ← تیم زیرساخت
        // ارسال ایمیل      ← تیم بازاریابی
    }
}
```

سه گروه مختلف می‌توانند باعث تغییر این کلاس شوند. یعنی سه دلیل برای تغییر = نقض SRP.

### چرا بد است؟

- تغییر فرمت ایمیل، ریسک شکستن منطق سفارش را دارد
- تست کردنش سخت است (برای تست اعتبارسنجی، به SMTP و دیتابیس نیاز داری)
- دو نفر نمی‌توانند همزمان رویش کار کنند بدون conflict

### راه‌حل

هر مسئولیت در کلاس خودش، و یک کلاس **هماهنگ‌کننده** که آن‌ها را به هم وصل می‌کند.

**هشدار:** SRP را هم می‌شود به افراط کشید. اگر برای هر متد یک کلاس بسازی، کدت غیرقابل‌خواندن می‌شود. معیار عملی: **آیا دو دلیل مستقل برای تغییر این کلاس وجود دارد؟**

---

## O — Open/Closed

> باز برای **توسعه**، بسته برای **تغییر**.

یعنی برای افزودن قابلیت جدید، نباید کد موجود و تست‌شده را دست بزنی.

### مثال نقض

```csharp
if (customerType == "Regular")  return amount * 0.05m;
if (customerType == "Gold")     return amount * 0.10m;
if (customerType == "Platinum") return amount * 0.20m;
```

هر نوع مشتری جدید = باز کردن این متد = ریسک شکستن انواع قبلی.

### راه‌حل

```csharp
public interface IDiscountPolicy
{
    decimal CalculateDiscount(decimal amount);
}
```

نوع جدید = کلاس جدید. کد موجود **اصلاً باز نمی‌شود**.

**نشانه نقض OCP:** هر بار که قابلیت جدیدی اضافه می‌کنی، مجبوری یک `switch` یا زنجیره `if` را ویرایش کنی.

**تذکر واقع‌بینانه:** نمی‌شود همه‌جا OCP را رعایت کرد. جایی این اصل را اعمال کن که **می‌دانی تغییر خواهد کرد** — نه برای هر چیزی، چون آن هم over-engineering است.

## L — Liskov Substitution

> هر جا از کلاس پدر استفاده می‌شود، باید بتوانی فرزند را جایش بگذاری **بدون اینکه چیزی بشکند**.

### مثال کلاسیک: مربع و مستطیل

```csharp
public void Test(Rectangle r)
{
    r.Width = 5;
    r.Height = 4;
    Console.WriteLine(r.Area());   // انتظار: 20
}
```

اگر `Square` پاس بدهی، خروجی **16** می‌شود — چون ست کردن `Height` عرض را هم عوض کرده.

**نکته مهم:** از نظر ریاضی مربع یک مستطیل است. ولی از نظر **رفتاری** نیست. LSP درباره رفتار است، نه تعریف لغوی.

### علائم نقض LSP

- فرزند متد پدر را `NotImplementedException` می‌دهد
- فرزند شرط ورودی را سخت‌گیرانه‌تر می‌کند
- کد جایی `if (x is SpecificChild)` دارد — یعنی جایگزینی واقعاً کار نمی‌کند

### راه‌حل

معمولاً یعنی سلسله‌مراتب وراثت اشتباه است. به‌جایش از interface مشترک استفاده کن.

## I — Interface Segregation

> کلاینت نباید مجبور شود به متدهایی وابسته باشد که استفاده نمی‌کند.

### مثال نقض

```csharp
public interface IMachine
{
    void Print(string doc);
    void Scan(string doc);
    void Fax(string doc);
}

public class OldPrinter : IMachine
{
    public void Print(string doc) { }
    public void Scan(string doc) => throw new NotImplementedException();   // ❌
    public void Fax(string doc) => throw new NotImplementedException();    // ❌
}
```

**قانون تشخیص:** هر جا `NotImplementedException` دیدی، احتمال زیادی نقض ISP است.

### راه‌حل

```csharp
public interface IPrinter { void Print(string doc); }
public interface IScanner { void Scan(string doc); }
public interface IFax     { void Fax(string doc); }
```

حالا هر دستگاه فقط آنچه واقعاً می‌تواند را اعلام می‌کند.

**ارتباط با SRP:** ISP در واقع همان SRP است ولی در سطح **اینترفیس** به‌جای کلاس.

## D — Dependency Inversion

> ماژول‌های سطح بالا نباید به ماژول‌های سطح پایین وابسته باشند. هر دو باید به **انتزاع** وابسته باشند.

### مثال نقض

```csharp
public class ReportService
{
    private readonly SqlOrderRepository _repo = new SqlOrderRepository();  // ❌
}
```

مشکلات:
- **تست‌ناپذیر** — برای تست کردن منطق گزارش، به SQL Server واقعی نیاز داری
- **غیرقابل‌تعویض** — نمی‌توانی منبع داده را عوض کنی
- منطق کسب‌وکار «می‌داند» که SQL Server وجود دارد

### راه‌حل

```csharp
public class ReportService
{
    private readonly IOrderRepository _repo;
    public ReportService(IOrderRepository repo) => _repo = repo;
}
```

حالا در تست می‌توانی `FakeOrderRepository` بدهی — بدون دیتابیس، سریع و قابل اتکا.

### تفاوت DI و DIP

این سوال را برای تشخیص عمق می‌پرسند:

- **DIP** یک **اصل طراحی** است: به انتزاع وابسته باش
- **Dependency Injection** یک **تکنیک** است: وابستگی را از بیرون بده
- **IoC Container** یک **ابزار** است (Autofac، Unity، Ninject) که تزریق را خودکار می‌کند

می‌توانی DIP را بدون container رعایت کنی — فقط با سازنده.

## جمع‌بندی برای مصاحبه

| اصل | سوالی که باید از خودت بپرسی |
|---|---|
| **S** | چند دلیل مستقل برای تغییر این کلاس وجود دارد؟ |
| **O** | برای افزودن نوع جدید، مجبورم کد موجود را باز کنم؟ |
| **L** | اگر فرزند را جای پدر بگذارم، چیزی می‌شکند؟ |
| **I** | آیا کسی مجبور است متدی را پیاده کند که لازم ندارد؟ |
| **D** | آیا این کلاس به کلاس مشخصی چسبیده یا به اینترفیس؟ |

**نکته‌ای که امتیاز می‌گیرد:** اگر پرسیدند «آیا همیشه باید SOLID را رعایت کرد؟» جواب خوب این است:

> «SOLID ابزار مدیریت تغییر است، نه هدف. در کدی که قرار است سال‌ها نگهداری شود ارزشش را دارد. در یک اسکریپت یک‌بارمصرف، فقط پیچیدگی اضافه می‌کند. من معمولاً از ساده شروع می‌کنم و وقتی دیدم جایی مدام در حال تغییر است، آنجا را با این اصول بازسازی می‌کنم.»
