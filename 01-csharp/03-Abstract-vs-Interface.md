# abstract class در برابر interface

## خلاصه یک‌خطی

`abstract class` می‌گوید موجودیت **چه چیزی هست**، `interface` می‌گوید **چه کاری می‌تواند بکند**.

---

## جدول تفاوت‌ها

| | abstract class | interface |
|---|---|---|
| پیاده‌سازی متد | می‌تواند داشته باشد | تا C# 7 نه، از C# 8 با default implementation بله |
| فیلد | بله | نه |
| سازنده (constructor) | بله | نه |
| سطح دسترسی اعضا | قابل تنظیم | همیشه public |
| چندتایی | فقط یکی | چندتا |
| نمونه‌سازی مستقیم | نه | نه |

---

## چه وقت کدام؟

**abstract class** وقتی:
- بین کلاس‌ها رابطه «هست» (is-a) برقرار است — کارمند تمام‌وقت **یک** کارمند **است**
- کد مشترکی داری که نمی‌خواهی در همه فرزندان تکرار شود
- می‌خواهی فیلد یا وضعیت مشترک داشته باشی

**interface** وقتی:
- قابلیتی داری که بین چیزهای **نامرتبط** مشترک است

در فایل کد، `Invoice` (فاکتور) هیچ ربطی به `Employee` ندارد، ولی هر دو `IReportable` هستند. این دقیقاً جایی است که interface درست است و abstract class غلط.

**در عمل معمولاً هر دو را با هم استفاده می‌کنی** — همان‌طور که `FullTimeEmployee` هم از `Employee` ارث می‌برد و هم دو interface را پیاده‌سازی می‌کند.

## abstract در برابر virtual

```csharp
public abstract decimal CalculateSalary();    // فرزند حتماً باید بنویسد
public virtual string Describe() => "...";    // پیش‌فرض دارد، فرزند می‌تواند عوض کند
```

- `abstract` → بدنه ندارد، پیاده‌سازی **اجباری** است
- `virtual` → بدنه دارد، بازنویسی **اختیاری** است

در فایل کد، `Contractor` متد `Describe` را override نکرده، پس نسخه پدر استفاده می‌شود. ولی مجبور بوده `CalculateSalary` را بنویسد.

## تله کلاسیک: `new` در برابر `override`

این سوال را عمداً می‌پرسند تا ببینند polymorphism را واقعاً فهمیده‌ای یا نه:

```csharp
Parent a = new ChildOverride();
a.Who();          // "Child"

Parent b = new ChildNew();
b.NonVirtual();   // "Parent"  ← تعجب کردی؟
```

**چرا؟**

- `override` → **Runtime Polymorphism**. کامپایلر نمی‌داند کدام نسخه اجرا می‌شود؛ در زمان اجرا بر اساس **نوع واقعی آبجکت** تصمیم گرفته می‌شود.
- `new` → فقط متد پدر را **پنهان** می‌کند. تصمیم در زمان کامپایل بر اساس **نوع متغیر** گرفته می‌شود، نه نوع آبجکت.

پس در خط دوم، چون نوع متغیر `Parent` است، نسخه `Parent` اجرا می‌شود — حتی با اینکه آبجکت واقعی `ChildNew` است.

**جمع‌بندی:** `new` تقریباً همیشه نشانه اشتباه طراحی است. اگر می‌خواهی رفتار را عوض کنی، متد پدر را `virtual` کن و در فرزند `override` بزن.

## Polymorphism در عمل

به `PayrollService.TotalPayroll` نگاه کن:

```csharp
foreach (var item in items)
    total += item.CalculatePay();
```

این متد نمی‌داند هر آیتم دقیقاً چیست — کارمند تمام‌وقت، پیمانکار، یا هر چیز دیگری که فردا اضافه شود. فقط می‌داند قرارداد `IPayable` را رعایت کرده.

**این دقیقاً اصل Open/Closed از SOLID است:** برای افزودن نوع جدید، این متد اصلاً لازم نیست تغییر کند.

---

## سوال تکمیلی احتمالی

> «از C# 8 که interface می‌تواند پیاده‌سازی پیش‌فرض داشته باشد، پس دیگر abstract class لازم نیست؟»

**نه.** interface همچنان نمی‌تواند **فیلد** یا **سازنده** یا **وضعیت** داشته باشد. اگر کلاس‌های فرزندت داده مشترک دارند، باز هم abstract class لازم است.

default implementation در interface بیشتر برای این اضافه شد که بتوانی به یک interface موجود متد جدید اضافه کنی بدون اینکه تمام کدهایی که آن را پیاده‌سازی کرده‌اند بشکنند.
