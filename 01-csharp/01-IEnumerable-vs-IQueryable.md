# IEnumerable در برابر IQueryable

## خلاصه یک‌خطی

`IEnumerable` فیلتر را **در حافظه** انجام می‌دهد، `IQueryable` آن را به **SQL ترجمه** می‌کند و در دیتابیس اجرا می‌شود.

---

## فرق اصلی در چیست؟

هر دو یک اینترفیس برای پیمایش مجموعه‌اند، ولی چیزی که نگه می‌دارند فرق دارد:

| | IEnumerable | IQueryable |
|---|---|---|
| چه چیزی نگه می‌دارد | خود داده‌ها | **درخت عبارت** (Expression Tree) |
| فیلتر کجا انجام می‌شود | در حافظه برنامه | در دیتابیس |
| فضای نام | `System.Collections` | `System.Linq` |
| مناسب برای | لیست، آرایه، داده‌ای که از قبل در حافظه است | دیتابیس، سرویس خارجی |

**درخت عبارت یعنی چی؟**

وقتی می‌نویسی `users.Where(u => u.Age > 30)` روی `IQueryable`، آن لامبدا **اجرا نمی‌شود**. به‌جایش به یک ساختار داده‌ای تبدیل می‌شود که می‌گوید «شرطی وجود دارد: ستون Age بزرگ‌تر از عدد ۳۰».

Entity Framework این ساختار را می‌خواند و به `WHERE Age > 30` ترجمه می‌کند.

روی `IEnumerable` اما آن لامبدا یک تابع معمولی C# است که باید روی هر عنصر اجرا شود — و برای اجرا شدن، عنصر باید در حافظه باشد.

---

## چرا این‌قدر مهم است؟

به متد `Wrong()` در فایل کد نگاه کن. تنها تفاوتش با `Right()` یک کلمه است، ولی:

- `Right()` → `SELECT * FROM Users WHERE Age > 30` → مثلاً ۲۰۰ رکورد برمی‌گردد
- `Wrong()` → `SELECT * FROM Users` → تمام ۵ میلیون رکورد وارد RAM می‌شود

در محیط تست با ۱۰۰ رکورد، هر دو درست کار می‌کنند و کسی متوجه نمی‌شود. در محیط واقعی، دومی سرور را می‌خواباند.

---

## Deferred Execution — اجرای تأخیری

به متد `BuildQueryStepByStep` نگاه کن:

```csharp
IQueryable<User> query = _db.Users;
if (minAge.HasValue)
    query = query.Where(u => u.Age >= minAge.Value);
if (onlyActive)
    query = query.Where(u => u.IsActive);
return query.ToList();   // ← تنها اینجا به دیتابیس می‌رویم
```

تا قبل از `ToList()` هیچ ارتباطی با دیتابیس برقرار نشده. فقط داریم درخت عبارت را می‌سازیم.

**توابعی که کوئری را اجرا می‌کنند:** `ToList`، `ToArray`، `Count`، `First`، `FirstOrDefault`، `Any`، `Single`، `Sum`، و `foreach`.

این ویژگی خیلی مفید است: می‌توانی فیلترها را شرطی و تدریجی بسازی و در نهایت یک کوئری بهینه تولید شود.

---

## تله‌ای که در کد واقعی زیاد می‌بینی

```csharp
var all = _db.Users.ToList();          // همه‌چیز می‌آید در حافظه
return all.Where(u => u.Age > 30);     // فیلتر در حافظه
```

این کد **نتیجه درستی می‌دهد** و برای همین کسی متوجه اشتباهش نمی‌شود. ولی از نظر کارایی همان فاجعه است.

قانون: `ToList()` را تا آخرین لحظه ممکن به تعویق بینداز.

---

## وقتی چیزی قابل ترجمه به SQL نیست

اگر داخل `Where` یک متد سفارشی C# صدا بزنی، EF نمی‌داند آن را چطور به SQL تبدیل کند و خطا می‌دهد.

راه‌حل: تا جایی که می‌شود در SQL فیلتر کن، بعد با `AsEnumerable()` وارد حافظه شو:

```csharp
_db.Users
   .Where(u => u.IsActive)    // در SQL
   .AsEnumerable()            // از اینجا به بعد در حافظه
   .Where(u => MyCheck(u))    // در C#
   .ToList();
```

نکته مهم: ترتیب اهمیت دارد. هرچه بیشتر قبل از `AsEnumerable` فیلتر کنی، داده کمتری وارد حافظه می‌شود.

---

## سوال تکمیلی که ممکن است بپرسند

> «پس همیشه IQueryable بهتر است؟»

نه. اگر `IQueryable` را از لایه Repository به بیرون بدهی، لایه‌های بالاتر می‌توانند به آن شرط اضافه کنند. یعنی **جزئیات دیتابیس به لایه UI نشت کرده** و دیگر نمی‌دانی چه کوئری‌ای واقعاً اجرا می‌شود.

بعضی تیم‌ها عمداً خروجی Repository را `IEnumerable` یا `List` می‌کنند تا این اتفاق نیفتد و کنترل کوئری‌ها متمرکز بماند.

**جواب خوب:** هر دو طرف را بگو و بگو انتخابت به معماری تیم بستگی دارد.

---

## جمله‌ای که سر مصاحبه بگو

> «IEnumerable فیلتر را در حافظه انجام می‌دهد و IQueryable آن را به SQL ترجمه می‌کند. برای همین در کوئری‌های دیتابیس همیشه IQueryable نگه می‌دارم و ToList را تا آخر به تعویق می‌اندازم. البته اگر بخواهم جلوی نشت کوئری به لایه‌های بالاتر را بگیرم، عمداً در مرز Repository آن را می‌بندم.»
