# Repository و Unit of Work

پرکاربردترین الگوها در پروژه‌های .NET سازمانی — و پرتکرارترین سوال الگو در مصاحبه.

---

## Repository چیست؟

**تعریف:** لایه‌ای که دسترسی به داده را پشت یک رابط مجموعه‌مانند پنهان می‌کند.

از دید کدی که استفاده‌اش می‌کند، Repository یک **مجموعه در حافظه** به‌نظر می‌رسد:

```csharp
var customer = _repo.GetById(5);
_repo.Add(newCustomer);
```

اینکه پشت صحنه SQL Server است یا فایل یا API، پنهان می‌ماند.

## چه مشکلی را حل می‌کند؟

**۱. تست‌پذیری** — این مهم‌ترین دلیل است.

بدون Repository، برای تست منطق کسب‌وکار باید یک SQL Server واقعی داشته باشی. با Repository، یک پیاده‌سازی ساختگی می‌دهی و تست در چند میلی‌ثانیه اجرا می‌شود.

**۲. جلوگیری از پخش شدن کوئری‌ها** — بدون Repository، کوئری‌های EF در همه‌جای پروژه پخش می‌شوند. با Repository، همه در یک جا متمرکزند.

**۳. امکان تعویض منبع داده** — در تئوری می‌توانی از EF به Dapper مهاجرت کنی بدون دست زدن به منطق. (در عمل به‌ندرت پیش می‌آید، ولی دلیل خوبی برای گفتن است.)

---

## Repository عمومی در برابر اختصاصی

```csharp
// عمومی — عملیات مشترک همه موجودیت‌ها
public interface IRepository<T> where T : class
{
    T GetById(int id);
    IEnumerable<T> GetAll();
    void Add(T entity);
}

// اختصاصی — کوئری‌های خاص یک موجودیت
public interface IOrderRepository : IRepository<Order>
{
    IEnumerable<Order> GetRecentOrders(int customerId, int days);
    decimal GetTotalSpent(int customerId);
}
```

در عمل معمولاً هر دو را داری: پایه عمومی برای CRUD تکراری، و ارث‌بری اختصاصی برای کوئری‌های خاص.

---

## Unit of Work چیست؟

**تعریف:** الگویی که چند عملیات را در **یک تراکنش** مدیریت می‌کند.

## چرا لازم است؟

فرض کن می‌خواهی سفارشی ثبت کنی که هم‌زمان:
- یک رکورد در جدول `Orders` بسازد
- موجودی انبار را در `Products` کم کند
- یک رکورد در `AuditLog` بنویسد

اگر هر Repository جداگانه `SaveChanges` بزند، ممکن است اولی موفق شود و دومی شکست بخورد → **داده ناسازگار**.

با Unit of Work، همه در یک تراکنش ذخیره می‌شوند:

```csharp
_uow.Orders.Add(order);
_uow.Products.Update(product);
_uow.Complete();    // ← یا همه، یا هیچ‌کدام
```

## نکته طراحی مهم

به کد نگاه کن: **در کلاس `Repository` هیچ `SaveChanges` وجود ندارد.**

این عمدی است. Repository فقط تغییرات را ثبت می‌کند؛ **تصمیم درباره commit با Unit of Work است**.

اگر هر Repository خودش `SaveChanges` بزند، دیگر نمی‌توانی چند عملیات را اتمیک کنی — و کل فایده الگو از بین می‌رود.

---

## بحث مهم: آیا EF خودش این الگو نیست؟

این سوال را عمداً می‌پرسند تا ببینند فقط کپی می‌کنی یا فکر می‌کنی.

**واقعیت:** بله. `DbContext` خودش یک Unit of Work است و `DbSet<T>` خودش یک Repository است.

پس گذاشتن Repository روی EF یعنی **یک لایه انتزاع روی یک لایه انتزاع دیگر**.

### جواب متعادل و حرفه‌ای

> «تکنیکاً درست است — DbContext خودش Unit of Work و DbSet خودش Repository است. من این لایه را وقتی اضافه می‌کنم که واقعاً فایده‌ای داشته باشد: مثلاً وقتی می‌خواهم منطق کسب‌وکار را بدون دیتابیس تست کنم، یا وقتی کوئری‌های پیچیده تکراری دارم که می‌خواهم در یک جا متمرکز باشند.
>
> ولی اگر پروژه کوچک است و مستقیم با EF کار می‌کنم، اضافه کردن این لایه فقط کد اضافه می‌سازد. در آن حالت DbContext را مستقیم تزریق می‌کنم.»

این جواب نشان می‌دهد الگو را **می‌فهمی**، نه اینکه از روی آموزش کپی کرده‌ای.

## اشتباهات رایج در پیاده‌سازی

**۱. برگرداندن `IQueryable` از Repository**

```csharp
IQueryable<Order> GetAll();    // ❌
```

با این کار لایه بالاتر می‌تواند به کوئری شرط اضافه کند — یعنی جزئیات دیتابیس به لایه UI نشت کرده و دیگر نمی‌دانی چه SQL ای اجرا می‌شود.

**۲. صدا زدن `SaveChanges` داخل Repository** — همان‌طور که بالا گفته شد، تراکنش را می‌شکند.

**۳. ساختن `DbContext` جدید در هر Repository**

اگر هر Repository کانتکست خودش را بسازد، دیگر در یک تراکنش نیستند. همه باید **یک نمونه مشترک** بگیرند — که وظیفه Unit of Work است.

**۴. Repository خیلی عمومی**

اگر فقط `IRepository<T>` داشته باشی و تمام کوئری‌ها را با `Find(predicate)` بنویسی، عملاً هیچ انتزاعی نساخته‌ای — فقط یک لایه اضافه گذاشته‌ای.

## طول عمر (Lifetime)

در ASP.NET، `DbContext` و در نتیجه `UnitOfWork` باید **per-request** باشند:
- یک نمونه برای هر درخواست HTTP
- در پایان درخواست `Dispose` شود

**چرا نه Singleton؟** چون Change Tracker مدام باد می‌کند و حافظه پر می‌شود. ضمناً `DbContext` thread-safe نیست.

**چرا نه per-call؟** چون آن‌وقت عملیات مختلف در یک درخواست، در تراکنش‌های جدا خواهند بود.
