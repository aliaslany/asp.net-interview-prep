# async / await

## خلاصه یک‌خطی

`async/await` رشته را در زمان انتظار **آزاد** می‌کند تا به درخواست دیگری برسد — نه اینکه کار را سریع‌تر کند.

---

## دقیقاً چه اتفاقی می‌افتد؟

فرض کن سرور تو ۱۰۰ رشته دارد و هر درخواست ۲ ثانیه منتظر دیتابیس می‌ماند.

**بدون async:** هر رشته ۲ ثانیه بلاک و بی‌کار منتظر می‌ماند. با ۱۰۰ درخواست همزمان، رشته‌ای باقی نمی‌ماند و درخواست ۱۰۱ در صف می‌ماند.

**با async:** وقتی به `await` می‌رسیم، رشته آزاد می‌شود و به درخواست بعدی می‌رسد. وقتی جواب دیتابیس آمد، یک رشته (احتمالاً رشته دیگری) کار را ادامه می‌دهد.

**نکته مهم:** async **کار را سریع‌تر نمی‌کند**. یک درخواست همان ۲ ثانیه طول می‌کشد. چیزی که بهتر می‌شود، **ظرفیت** سرور است.

---

## مهم‌ترین قانون: async برای I/O است، نه CPU

| نوع کار | مناسب است؟ |
|---|---|
| کوئری دیتابیس | ✓ |
| درخواست HTTP | ✓ |
| خواندن/نوشتن فایل | ✓ |
| محاسبات ریاضی سنگین | ✗ |
| پردازش تصویر | ✗ |

**چرا برای CPU بی‌فایده است؟** چون وقتی CPU مشغول محاسبه است، رشته‌ای آزاد نمی‌شود. هیچ انتظاری در کار نیست که بشود ازش استفاده کرد.

---

## تله شماره یک: `.Result` و `.Wait()`

این احتمالاً پرتکرارترین سوال async در مصاحبه‌های .NET Framework است.

```csharp
public string Bad()
{
    return GetDataAsync(url).Result;   // ❌ Deadlock
}
```

**چرا deadlock می‌شود؟**

۱. رشته اصلی روی `.Result` بلاک می‌شود و منتظر نتیجه می‌ماند
۲. عملیات async تمام می‌شود و می‌خواهد ادامه کار را روی **همان SynchronizationContext** اجرا کند
۳. ولی آن context توسط رشته بلاک‌شده اشغال شده است
۴. هر دو برای همیشه منتظر هم می‌مانند

**راه‌حل:** متد را `async` کن و `await` بزن — از بالا تا پایین.

```csharp
public async Task<string> Good()
{
    return await GetDataAsync(url);
}
```

**نکته:** در **ASP.NET Core** این SynchronizationContext حذف شده، پس این deadlock رخ نمی‌دهد. ولی در **ASP.NET Framework** (که آگهی این شرکت به آن اشاره دارد) کاملاً واقعی است. گفتن این تفاوت، امتیاز خوبی دارد.

---

## اجرای موازی با `Task.WhenAll`

```csharp
// ❌ پشت سر هم — ۳ ثانیه
var a = await GetAsync("a");
var b = await GetAsync("b");
var c = await GetAsync("c");

// ✅ همزمان — ۱ ثانیه
var ta = GetAsync("a");
var tb = GetAsync("b");
var tc = GetAsync("c");
var results = await Task.WhenAll(ta, tb, tc);
```

**نکته کلیدی:** تسک‌ها به محض ساخته شدن شروع می‌شوند. با ننوشتن `await` پشت هر کدام، اجازه می‌دهیم همه همزمان بروند و بعد منتظر همه می‌مانیم.

فقط حواست باشد این وقتی درست است که کارها **به هم وابسته نباشند**. اگر `b` به نتیجه `a` نیاز دارد، مجبوری پشت سر هم بروی.

---

## `async void` — تقریباً همیشه اشتباه

```csharp
public async void Bad() { throw new Exception(); }    // ❌ برنامه crash می‌کند
public async Task Good() { throw new Exception(); }   // ✅ قابل catch
```

با `async void`:
- خطا قابل گرفتن نیست و به سطح بالا می‌رود و پروسه را می‌کشد
- نمی‌توانی `await` کنی، پس نمی‌دانی کِی تمام شده

**تنها استثنا:** event handler ها، چون امضایشان اجازه `Task` نمی‌دهد.

---

## `ConfigureAwait(false)`

```csharp
var data = await _http.GetStringAsync(url).ConfigureAwait(false);
```

یعنی: «لازم نیست ادامه کار را روی context اصلی اجرا کنی، هر رشته‌ای باشد کافی است.»

**کجا استفاده کن؟** در کد کتابخانه‌ای و لایه‌های داخلی — هم کارایی بهتر است، هم ریسک deadlock را از بین می‌برد.

**کجا نه؟** در لایه UI (WinForms/WPF) که بعد از await می‌خواهی به کنترل‌های فرم دست بزنی، چون آن‌ها فقط از رشته UI قابل دسترسی‌اند.

---

## چند نکته کوتاه

**`Task` در برابر `Thread`:** `Thread` یک رشته واقعی سیستم‌عامل است (پرهزینه، حدود ۱ مگابایت حافظه). `Task` یک انتزاع سطح بالاتر است که از Thread Pool استفاده می‌کند — سبک‌تر و قابل ترکیب.

**`Task.Run` کِی؟** برای انتقال کار **CPU-سنگین** به رشته دیگر. در برنامه دسکتاپ مفید است تا UI فریز نشود. در **وب‌سرور معمولاً اشتباه است**، چون فقط کار را از یک رشته thread pool به رشته دیگرِ همان pool منتقل می‌کند — سودی ندارد.

**نام‌گذاری:** طبق قرارداد، متدهای async را با پسوند `Async` نام‌گذاری کن: `GetUserAsync`.

---

## جمله‌ای که سر مصاحبه بگو

> «async برای I/O است نه CPU. در ASP.NET Framework هیچ‌وقت روی متد async از .Result یا .Wait استفاده نمی‌کنم چون deadlock می‌دهد — به‌جایش از بالا تا پایین async می‌نویسم. و اگر چند کار مستقل داشته باشم، به‌جای await پشت سر هم، با Task.WhenAll موازی اجرایشان می‌کنم.»
