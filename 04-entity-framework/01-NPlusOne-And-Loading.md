# مشکل N+1 و انواع بارگذاری در EF

رایج‌ترین مشکل عملکردی در پروژه‌های Entity Framework — و سوالی که تقریباً حتماً پرسیده می‌شود.

---

## مشکل N+1 چیست؟

```csharp
var orders = _db.Orders.Take(1000).ToList();     // ۱ کوئری

foreach (var order in orders)
    Console.WriteLine(order.Customer.Name);       // ۱۰۰۰ کوئری!
```

جمعاً **۱۰۰۱ رفت‌وبرگشت** به دیتابیس. اسمش N+1 است: یک کوئری اصلی + N کوئری فرعی.

## چرا اتفاق می‌افتد؟

به‌خاطر **Lazy Loading**. خاصیت `Customer` با کلیدواژه `virtual` تعریف شده:

```csharp
public virtual Customer Customer { get; set; }
```

EF در زمان اجرا یک کلاس proxy می‌سازد که این خاصیت را override می‌کند. به محض اینکه به آن دست بزنی، proxy یک کوئری می‌زند.

## چرا این‌قدر بد است؟

مشکل اصلی حجم داده نیست — **تأخیر شبکه** است.

هر رفت‌وبرگشت به دیتابیس حتی اگر فقط ۱ میلی‌ثانیه باشد، ۱۰۰۰ تایش می‌شود ۱ ثانیه. و این فقط تأخیر است، بدون احتساب زمان خود کوئری.

**بدتر اینکه:** در محیط توسعه با ۱۰ رکورد تست، هیچ‌کس متوجه نمی‌شود. مشکل فقط در پروداکشن خودش را نشان می‌دهد.

---

## سه راه‌حل

### ۱. Eager Loading با `Include`

```csharp
var orders = _db.Orders
    .Include(o => o.Customer)
    .Take(1000)
    .ToList();
```

تبدیل می‌شود به یک `JOIN` واحد.

**هشدار — Cartesian Explosion:** اگر چند `Include` تودرتو بزنی، داده تکراری زیادی برمی‌گردد. مثلاً اگر مشتری ۱۰ سفارش داشته باشد، اطلاعات کامل مشتری ۱۰ بار در نتیجه تکرار می‌شود. با چند سطح Include، حجم نتیجه انفجاری بالا می‌رود.

### ۲. Explicit Loading

```csharp
_db.Entry(customer).Collection(c => c.Orders).Load();
_db.Entry(order).Reference(o => o.Customer).Load();
```

**کِی مفید است؟** وقتی فقط در شرایط خاصی به داده مرتبط نیاز داری. مثلاً فقط اگر کاربر روی «نمایش جزئیات» کلیک کرد.

### ۳. Projection — معمولاً بهترین

```csharp
var data = _db.Orders
    .Select(o => new OrderListItem
    {
        OrderId      = o.Id,
        Total        = o.Total,
        CustomerName = o.Customer.Name
    })
    .ToList();
```

**چرا بهترین است؟**
- فقط ستون‌های لازم از دیتابیس می‌آید، نه کل موجودیت
- Change Tracker اصلاً درگیر نمی‌شود (خروجی موجودیت EF نیست)
- کمترین ترافیک شبکه و حافظه
- بدون خطر Cartesian Explosion

**قاعده عملی:** برای صفحات **نمایش و گزارش** همیشه Projection. برای عملیاتی که قرار است داده را **تغییر** دهی، موجودیت کامل با Include.

## AsNoTracking

```csharp
_db.Orders.AsNoTracking().Where(...).ToList();
```

### Change Tracker چه می‌کند؟

EF از هر موجودیتی که از دیتابیس می‌آورد یک **عکس اولیه** نگه می‌دارد. موقع `SaveChanges`، وضعیت فعلی را با آن عکس مقایسه می‌کند تا بفهمد چه چیزی عوض شده و فقط همان‌ها را `UPDATE` کند.

### چرا غیرفعالش کنیم؟

اگر قرار نیست چیزی را آپدیت کنی، این کار:
- حافظه می‌خورد (نگهداری عکس هر رکورد)
- CPU می‌خورد (مقایسه موقع SaveChanges)
- و هیچ فایده‌ای ندارد

در لیست‌های بزرگ، تفاوت کارایی کاملاً محسوس است.

**جمله‌ای که سر مصاحبه بگو:**
> «در صفحات گزارش و لیست که فقط خواندنی هستند، همیشه AsNoTracking می‌گذارم.»

این نشان می‌دهد با EF در **پروداکشن** کار کرده‌ای، نه فقط در آموزش.

## تله: Lazy Loading بعد از بسته شدن Context

```csharp
using (var db = new ShopContext())
{
    orders = db.Orders.ToList();
}   // context بسته شد

Console.WriteLine(orders[0].Customer.Name);   // ❌ ObjectDisposedException
```

Lazy Loading می‌خواهد کوئری بزند ولی context دیگر زنده نیست.

**راه‌حل:** قبل از بسته شدن context، هر چیزی که لازم داری را با `Include` یا `Select` بارگذاری کن.

---

## پیشنهاد عملی: Lazy Loading را خاموش کن

```csharp
_db.Configuration.LazyLoadingEnabled = false;
```

**چرا؟** چون اگر یادت برود `Include` بزنی، به‌جای اینکه بی‌صدا ۱۰۰۰ کوئری اضافه بزند، `null` می‌گیری و **زود متوجه می‌شوی**.

خطای زودهنگام بهتر از مشکل عملکردی نامرئی است. خیلی از تیم‌ها این را به‌عنوان قانون پروژه دارند.

## چطور این مشکل را تشخیص بدهی؟

- **SQL Server Profiler** یا **Extended Events** — تعداد واقعی کوئری‌ها را می‌بینی
- **لاگ کردن SQL در EF:**
  ```csharp
  _db.Database.Log = s => System.Diagnostics.Debug.WriteLine(s);
  ```
- **MiniProfiler** — تعداد و زمان کوئری‌ها را روی خود صفحه نشان می‌دهد

**نکته‌ای که امتیاز می‌گیرد:** اگر پرسیدند «چطور می‌فهمی مشکل N+1 داری؟»، جواب «SQL را لاگ می‌کنم و تعداد کوئری‌ها را می‌شمارم» خیلی بهتر از «از روی کد حدس می‌زنم» است.
